CI/CD 표준 가이드라인

PR 검사 → 버전 게이트 → 빌드 → 무중단 배포(Blue-Green) → 헬스체크 → 스모크 테스트 → 롤백. 사내 모든 서비스는 이 플로우를 따른다.

작성일 2026-07-30 · 기준 구현 nodi-be (GitHub Actions / GHCR / nginx) · Node.js 22 · 배포 방식 Docker PM2

1. 개요

배포 방식(Docker / PM2)은 팀이 고를 수 있지만 플로우와 안전장치는 고정이다. 어떤 레포를 열어도 같은 순서, 같은 파일 이름, 같은 실패 동작을 기대할 수 있어야 한다. 아래 3절·4절의 템플릿은 그 플로우를 각 방식으로 구현한 것이며, 복사해서 바로 쓰도록 되어 있다.

1.1 표준 플로우 원칙

원칙내용이유
PR 에서 전부 막는다 format · lint · test · build 를 PR 에서 실행하고, main 에서는 다시 검사하지 않는다 main 은 이미 검증된 커밋만 들어온다. 배포 경로를 짧게 유지
배포 트리거는 main push 하나 수동 배포는 workflow_dispatch 로만 허용 배포된 코드 = main 이라는 등식을 깨지 않는다
버전이 곧 릴리스 식별자 package.json 의 version 이 중복이면 빌드 전에 실패 같은 버전 두 개가 존재하면 무엇이 배포됐는지 추적 불가
전환 전에 검증 새 색이 전부 healthy 가 된 뒤에만 트래픽을 옮긴다 실패해도 사용자 영향 0. 현재 색은 손대지 않은 상태로 남는다
전환 후에도 검증 nginx 를 통과하는 스모크 테스트가 실패하면 자동 롤백 컨테이너는 healthy 인데 프록시 경로가 깨진 경우를 잡는다
이전 버전을 지우지 않는다 이전 색은 stop 까지만. 삭제하지 않는다 재빌드 없이 즉시 롤백. 직전 1버전은 항상 살아 있다
비밀은 레포에 없다 운영 .env 는 production Environment Secret 에서 배포 시점에 생성 레포 열람 권한과 운영 비밀 접근 권한을 분리

1.2 파이프라인 단계

1
PR 열림 · 갱신
pr-check.yml — format:check, lint:check, test:ci, build 하나라도 실패하면 머지 불가. 같은 PR 에 새 커밋이 오면 이전 실행은 취소한다.
2
main 에 머지
버전 게이트 — package.json 의 version 이 이미 릴리스됐는지 확인 Docker 는 GHCR 태그 조회, PM2 는 git 태그 조회. 중복이면 빌드 잡이 시작되지 않는다.
3
Docker
이미지 빌드 → GHCR push (latest, sha-..., v1.2.3) 배포 산출물이 레지스트리에 남는다. 롤백·재배포 때 다시 빌드하지 않는다.
3
PM2
dist 번들 빌드 → tar 아티팩트 업로드 네이티브 모듈·Prisma 엔진은 플랫폼에 묶이므로 node_modules 는 넣지 않고 서버에서 설치한다.
4
배포 (SSH)
.env.deploy 생성 → 배포 파일 SCP → 서버의 deploy.sh 실행 production Environment 를 쓰므로 승인 규칙을 붙일 수 있다.
5
Blue-Green 전환
반대 색 기동 → 헬스체크 → upstream 파일 교체 → nginx reload → 스모크 테스트 → 이전 색 stop 헬스체크 실패는 배포 취소(영향 0), 스모크 실패는 자동 롤백.

1.3 배포 방식 선택

DockerPM2

런타임 재현성 이미지에 고정 — 러너와 서버가 같은 것을 실행 서버의 Node·glibc 버전에 의존

2. 공통 규칙

2.1 브랜치와 트리거

브랜치역할실행되는 워크플로
main운영에 배포된 코드배포 워크플로 (push 시)
develop통합 브랜치. 여기서 main 으로 PR—
feature/*작업 브랜치PR 검사 (PR 열릴 때)

main 브랜치에는 직접 push 를 막고 PR 검사를 required status check 로 지정한다 (Settings → Branches → Branch protection rules).

2.2 concurrency

두 워크플로의 cancel-in-progress 값이 반대인 것이 핵심이다.

워크플로groupcancel-in-progress이유
PR 검사 pr-check-${PR번호} true 새 커밋이 오면 옛 커밋 검사는 의미가 없다. 러너 시간 절약
배포 build-and-deploy-${ref} false 취소되면 blue-green 전환이 중간에 끊긴다. upstream 은 새 색인데 헬스체크 전이거나, 이전 색이 안 내려간 상태로 남는다

2.3 버전 게이트

package.json 의 version 을 올리지 않고 머지하면 빌드 전에 실패한다. 검사만 하는 잡을 따로 두고 needs 로 묶어서, 중복이면 비싼 빌드 잡이 아예 시작되지 않게 한다.

  • Docker docker manifest inspect 로 GHCR 에 v{version} 태그가 있는지 확인
  • PM2 git ls-remote --tags 로 v{version} 태그가 있는지 확인 → 배포 성공 후 태그 push

버전 표기는 v 접두사를 붙인다(v1.2.3). 이미지 태그·git 태그·릴리스 노트에서 같은 문자열을 쓴다.

2.4 시크릿과 변수

배포 잡은 environment: production 을 지정한다. 이 Environment 에 시크릿을 두면 다른 브랜치의 워크플로가 접근하지 못하고, 필요하면 승인(required reviewers)도 걸 수 있다.

이름종류값
PROD_ENV_FILESecret운영 .env 파일 전체 내용
PROD_SSH_HOSTSecret운영 서버 호스트
PROD_SSH_PORTSecretSSH 포트
PROD_SSH_USERSecret배포 계정
PROD_SSH_PRIVATE_KEYSecret배포 계정 개인키
PROD_SSH_FINGERPRINTSecret서버 호스트키 지문 — 중간자 공격 방지용, 생략하지 말 것
PROD_DEPLOY_PATHVariable서버의 배포 디렉터리 (예: /srv/app)
GHCR_IMAGEVariableDocker ghcr.io/owner/repo

GHCR push 에는 별도 토큰이 필요 없다. 기본 GITHUB_TOKEN 에 packages: write 권한만 주면 된다.

2.5 무중단 전환 원리

nginx 설정 한 줄만 담긴 파일을 include 해두고, 배포 스크립트가 그 파일을 덮어쓴 뒤 nginx -s reload 를 호출한다. reload 는 기존 워커가 처리 중인 요청을 끝낸 뒤 교체되므로 연결이 끊기지 않는다. 

nginx/active/upstream.conf   ←  이 파일이 "지금 어느 색이 활성인가"의 유일한 정답
  set $upstream backend_blue:3000;

nginx/conf.d/default.conf
  location / {
      include /etc/nginx/active/upstream.conf;
      proxy_pass http://$upstream;
  }

이 파일은 배포 산출물이 아니라 서버의 상태다. CI 의 SCP 대상에 절대 넣지 말 것. 넣으면 배포할 때마다 활성 색이 레포에 커밋된 값으로 되돌아가면서, 실제로 떠 있는 색과 어긋난다(= 트래픽이 죽은 색으로 간다).

2.6 헬스체크·스모크·롤백 계약

애플리케이션은 GET /health 를 제공해야 한다. 인증 없이 200 을 반환하고, DB·Redis 연결 상태를 반영한다.

단계대상실패하면사용자 영향
헬스체크 새 색을 직접 (127.0.0.1:포트/health 또는 컨테이너 health) 새 색 제거, 배포 취소 없음 — 트래픽은 아직 현재 색
스모크 테스트 nginx 를 통과하는 경로 (127.0.0.1/health) upstream 되돌리고 reload, 새 색 제거 수 초 (전환 직후 실패한 요청만)
배포 후 발견 모니터링·알림 이전 색 start → upstream 되돌림 → reload 발견까지의 시간

헬스체크는 replica 전체가 healthy 여야 통과다. 하나라도 아니면 전환하지 않는다. 타임아웃은 90초, 폴링 3초를 기본값으로 한다.

2.7 PR 검사 템플릿 공통

Docker · PM2 어느 쪽이든 이 파일은 동일하다.

.github/workflows/pr-check.yml 
name: PR Check

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review]

permissions:
  contents: read

concurrency:
  group: pr-check-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  check:
    name: Format, lint, test, build
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      # Prisma Client 생성에는 URL 형식이 필요하지만 DB 연결은 하지 않는다.
      DATABASE_URL: mysql://ci:ci@localhost:3306/ci

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Generate Prisma Client
        run: npx prisma generate

      - name: Check formatting
        run: npm run format:check

      - name: Check lint
        run: npm run lint:check

      - name: Run tests
        run: npm run test:ci

      - name: Build
        run: npm run build

DATABASE_URL 은 Prisma Client 를 생성할 때 형식 검증에만 쓰인다. 실제 DB 에 접속하지 않으므로 더미 값이면 된다. 테스트가 실제 DB 를 필요로 하면 services: 로 컨테이너를 띄워 붙인다.

3.2 배포 워크플로

잡을 check-version → build-and-push → deploy 세 개로 나눈다. 버전이 중복이면 첫 잡에서 끝나므로 빌드 러너를 쓰지 않는다.

.github/workflows/build-image.yml 
name: Build and Push Image (arm64)

# main 에 push(=PR 머지) 될 때마다 arm64 이미지를 빌드해 GHCR 에 푸시
on:
  push:
    branches: [main]
  workflow_dispatch: # 필요 시 수동 실행

# 배포 도중 새 push 로 workflow 가 취소되면 blue-green 전환이 중간에 끊길 수 있다.
# 같은 브랜치의 실행은 취소하지 않고 순서대로 대기시킨다.
concurrency:
  group: build-and-deploy-${{ github.ref }}
  cancel-in-progress: false

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }} # 예: swyp-web-14th-7team/nodi-be

jobs:
  # ── 1) 버전 태그 중복 검사 ─────────────────────────────
  # package.json 의 version 이 이미 GHCR 에 있으면 실패 → build 잡이 안 돎(취소)
  # 레지스트리 조회만 하므로 저렴한 x86 러너 사용
  check-version:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: read # 태그 존재 확인용
    outputs:
      version: ${{ steps.pkg.outputs.version }}
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Read version from package.json
        id: pkg
        run: echo "version=$(node -p "require('./package.json').version")" >> "$GITHUB_OUTPUT"

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Fail if version tag already exists
        run: |
          IMAGE=$(echo "${{ env.IMAGE_NAME }}" | tr '[:upper:]' '[:lower:]')
          TAG="${{ env.REGISTRY }}/$IMAGE:v${{ steps.pkg.outputs.version }}"
          if docker manifest inspect "$TAG" >/dev/null 2>&1; then
            echo "::error::$TAG 이미 존재 — package.json version 을 올리세요."
            exit 1
          fi
          echo "$TAG 없음 → 빌드 진행"

  # ── 2) 이미지 빌드 & 푸시 ──────────────────────────────
  # check-version 성공 시에만 실행 (중복 버전이면 여기 도달 못 함)
  build-and-push:
    needs: check-version
    # arm64 네이티브 러너 → QEMU 에뮬레이션 없이 빠르게 arm64 빌드
    # (private repo 에서 arm 러너를 못 쓰는 플랜이면 runs-on: ubuntu-latest 로 바꾸고
    #  아래 'Set up QEMU' 스텝 주석을 해제할 것)
    runs-on: ubuntu-24.04-arm
    permissions:
      contents: read
      packages: write # GHCR 푸시 권한

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      # QEMU (에뮬레이션으로 arm64 빌드할 때만 필요 — 네이티브 arm 러너면 불필요)
      # - name: Set up QEMU
      #   uses: docker/setup-qemu-action@v3

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }} # 별도 시크릿 불필요

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          # latest + 커밋 SHA + package.json 버전 태그 부여
          # (SHA 는 불변 핀용, latest 는 최신, 버전은 사람이 읽는 릴리스 식별)
          tags: |
            type=raw,value=latest
            type=sha,format=long
            type=raw,value=v${{ needs.check-version.outputs.version }}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/arm64
          push: true
          # package.json 버전을 이미지에 주입 → node 직접 실행 시에도 Swagger 버전 표시
          build-args: |
            APP_VERSION=${{ needs.check-version.outputs.version }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          # GitHub Actions 캐시로 레이어 재사용 → 빌드 속도 향상
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ── 3) 운영 서버 배포 ──────────────────────────────────
  # 이미지 push 가 끝난 뒤 SSH 로 운영 서버에 접속해 이미지를 받고 배포 스크립트를 실행한다.
  deploy:
    needs: [check-version, build-and-push]
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read

    steps:
      # build job 과 runner 가 다르므로 SCP 로 보낼 파일을 다시 checkout 한다.
      - name: Checkout
        uses: actions/checkout@v4

      # 운영 환경변수는 저장소에 두지 않고 production Environment Secret으로 파일을 만든다.
      - name: Create deployment environment file
        env:
          PROD_ENV_FILE: ${{ secrets.PROD_ENV_FILE }}
        run: |
          if [ -z "$PROD_ENV_FILE" ]; then

3.5 nginx 설정

nginx/conf.d/default.conf 
# 앞단(호스트 nginx 등)이 보낸 X-Forwarded-Proto 가 있으면 그대로 신뢰하고,
# 없으면(도커 nginx 직접 접근) 현재 scheme 으로 fallback
map $http_x_forwarded_proto $forwarded_proto {
    default $http_x_forwarded_proto;
    ''      $scheme;
}

# 기본 combined 포맷은 평문이라 로그 수집기에서 필드로 못 거르고, 무엇보다 $request_id 가
# 남지 않아 백엔드 로그와 같은 요청으로 묶이지 않는다(502 처럼 백엔드에 줄이 없는 경우가 특히 문제).
# $upstream_addr 은 resolver 가 푼 IP 라 사람이 못 읽으므로, set 한 $upstream 도 target 으로 남겨 색을 식별한다.
log_format json_log escape=json '{'
    '"req_id":"$request_id",'
    '"method":"$request_method",'
    '"url":"$request_uri",'
    '"status":"$status",'
    '"target":"$upstream",'
    '"upstream_addr":"$upstream_addr",'
    '"upstream_status":"$upstream_status",'
    '"request_time":"$request_time",'
    '"upstream_time":"$upstream_response_time",'
    '"body_bytes":"$body_bytes_sent",'
    '"ip":"$remote_addr",'
    '"ua":"$http_user_agent"'
'}';

server {
    listen 80;
    server_name _;

    access_log /var/log/nginx/access.log json_log;

    # Docker 내부 DNS. proxy_pass 에 변수를 쓰면 nginx 가 기동 시점에 이름을 고정하지 않고
    # 매 요청 해석하므로, 컨테이너가 재생성돼 IP 가 바뀌어도 따라간다.
    resolver 127.0.0.11 valid=10s;
    client_max_body_size 6m;

    location / {
        # 활성 색(blue/green)을 가리키는 파일에서 $upstream 을 가져온다.
        # 배포 스크립트가 이 파일만 교체하고 reload → 무중단 전환
        include /etc/nginx/active/upstream.conf;
        proxy_pass http://$upstream;
        proxy_http_version 1.1;

        # 연결 실패/타임아웃 시 다음 replica 로 재시도
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
        proxy_next_upstream_timeout 10s;
        proxy_connect_timeout 5;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $forwarded_proto;
        # nginx 가 만든 요청 ID 를 백엔드로 전달 → 두 로그가 같은 req_id 로 묶인다
        proxy_set_header X-Request-Id      $request_id;
    }
}

액세스 로그를 JSON 으로 남기고 $request_id 를 백엔드로 전달하는 것이 표준이다. 백엔드 로거가 X-Request-Id 를 우선 사용하도록 만들면 nginx 로그와 앱 로그를 같은 ID 로 묶어 볼 수 있다. 502 처럼 백엔드에 로그가 아예 없는 장애에서 특히 중요하다.

3.6 배포 스크립트

scripts/deploy.sh 
#!/usr/bin/env bash
# ─────────────────────────────────────────────────────────────
# Blue-Green 무중단 배포 스크립트
#
# 흐름:
#   1) 현재 활성 색 파악 (nginx/active/upstream.conf 에서 읽음)
#   2) 반대 색을 새 이미지로 기동
#   3) 새 색 헬스체크 (★ 전환 전에! 모든 replica 가 healthy 될 때까지)
#        실패 → 새 색 종료, 배포 취소 (현재 색 무사 = 사용자 영향 0)
#   4) upstream.conf 를 새 색으로 교체
#   5) nginx reload (graceful = 무중단 전환)
#   6) 스모크 테스트 (nginx 통해 실제 200 응답 확인)
#        실패 → upstream 롤백 + reload, 새 색 종료 (현재 색 복귀)
#   7) 이전 색 종료
#
# 최초 부팅(둘 다 없을 때)은 먼저 아래로 띄운 뒤 이 스크립트를 사용:
#   docker compose up -d              # blue + nginx + 로그 수집 스택(loki/alloy/grafana)
#
# 사용법:
#   docker compose pull               # ★ 먼저! GHCR 에서 새 이미지를 받아둘 것
#   ./scripts/deploy.sh
#
# ★ 이 스크립트는 pull 하지 않는다. 받아둔 로컬 이미지로만 배포하므로,
#   pull 을 빼먹으면 옛 이미지가 그대로 다시 뜨고 헬스체크·스모크 테스트는 통과한다
#   (= 배포된 줄 알지만 코드는 그대로). compose 는 캐시된 태그를 다시 받지 않음.
# ─────────────────────────────────────────────────────────────
set -euo pipefail

# 프로젝트 루트로 이동 (스크립트가 어디서 실행되든 동일하게 동작)
cd "$(dirname "$0")/.."

ACTIVE_FILE="./nginx/active/upstream.conf"
NGINX_SVC="nginx"
HEALTH_TIMEOUT=90      # 새 색 헬스체크 최대 대기(초)
POLL_INTERVAL=3        # 헬스체크 폴링 간격(초)

log()  { printf '\033[1;34m[deploy]\033[0m %s\n' "$*"; }
warn() { printf '\033[1;33m[deploy:warn]\033[0m %s\n' "$*"; }
err()  { printf '\033[1;31m[deploy:error]\033[0m %s\n' "$*" >&2; }

# 색 → compose profile 인자 (blue 는 profile 없음, green 만 "green")
profile_args() { [ "$1" = "green" ] && printf -- '--profile green' || printf ''; }

# 지정한 backend 서비스의 모든 replica가 healthy가 될 때까지 기다린다.
wait_for_health() {
  local service="$1"
  local profile="$2"
  local elapsed=0

  log "$service 헬스체크 대기 (최대 ${HEALTH_TIMEOUT}s, replica 전체 healthy 필요)..."
  while :; do
    # shellcheck disable=SC2086
    ids=$(docker compose $profile ps -q "$service")
    total=0; healthy=0
    for id in $ids; do
      total=$((total + 1))
      status=$(docker inspect --format '{{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}' "$id" 2>/dev/null || echo none)
      [ "$status" = "healthy" ] && healthy=$((healthy + 1))
    done
    log "  healthy ${healthy}/${total:-0}"

    if [ "$total" -gt 0 ] && [ "$healthy" -eq "$total" ]; then
      log "✅ $service 전체 healthy"
      return 0
    fi

    if [ "$elapsed" -ge "$HEALTH_TIMEOUT" ]; then
      err "$service 헬스체크 실패"
      return 1
    fi
    sleep "$POLL_INTERVAL"
    elapsed=$((elapsed + POLL_INTERVAL))
  done
}

# ── 0) 최초 기동 ───────────────────────────────────────────────
# nginx가 실행 중이 아니면 아직 compose stack이 준비되지 않은 것으로 보고 전체를 blue로 기동한다.
if [ -z "$(docker compose ps -q "$NGINX_SVC")" ]; then
  log "실행 중인 nginx가 없음 → 최초 compose 기동"
  mkdir -p "$(dirname "$ACTIVE_FILE")"
  printf 'set $upstream backend_blue:3000;\n' > "$ACTIVE_FILE"

  docker compose up -d

  if ! wait_for_health "backend_blue" ""; then
    err "최초 기동 실패"
    exit 1
  fi

  log "최초 기동 스모크 테스트 (http://localhost:8080/health)..."
  if ! curl -fsS -m 5 http://localhost:8080/health > /dev/null; then
    err "최초 기동 스모크 테스트 실패"
    exit 1
  fi

  log "🎉 최초 compose 기동 성공: blue 활성"
  exit 0
fi

# ── 1) 현재 활성 색 파악 ──────────────────────────────────────
if [ ! -f "$ACTIVE_FILE" ]; then
  err "$ACTIVE_FILE 가 없습니다. 먼저 'set \$upstream backend_blue:3000;' 로 생성하세요."
  exit 1
fi

if grep -q backend_green "$ACTIVE_FILE"; then
  CURRENT=green; NEXT=blue
else
  CURRENT=blue;  NEXT=green
fi

CUR_SVC="backend_$CURRENT"
NEXT_SVC="backend_$NEXT"
CUR_PROFILE=$(profile_args "$CURRENT")
NEXT_PROFILE=$(profile_args "$NEXT")

log "현재 활성: $CURRENT  →  새로 배포: $NEXT"

# ── 2) 새 색 기동 ─────────────────────────────────────────────
log "$NEXT_SVC 기동..."
# shellcheck disable=SC2086
docker compose $NEXT_PROFILE up -d "$NEXT_SVC"

# ── 3) 새 색 헬스체크 (전환 전!) ──────────────────────────────
if ! wait_for_health "$NEXT_SVC" "$NEXT_PROFILE"; then
  err "$NEXT_SVC 헬스체크 실패 → 배포 취소 (현재 색 $CURRENT 무사)"
  # shellcheck disable=SC2086
  docker compose $NEXT_PROFILE rm -sf "$NEXT_SVC" || true
  exit 1
fi

# ── 4) upstream 전환 ──────────────────────────────────────────
log "upstream → $NEXT_SVC 로 전환"
printf 'set $upstream %s:3000;\n' "$NEXT_SVC" > "$ACTIVE_FILE"

# ── 5) nginx reload (무중단) ──────────────────────────────────
log "nginx reload (graceful)"
docker compose exec -T "$NGINX_SVC" nginx -s reload
sleep 2   # 워커 교체 + DNS 재해석 잠깐 대기

# ── 6) 스모크 테스트 (nginx 통해 실제 응답 확인) ──────────────
log "스모크 테스트 (http://localhost/health)..."
if ! curl -fsS -m 5 http://localhost:8080/health > /dev/null; then
  err "스모크 테스트 실패 → 롤백 ($CURRENT 로 복귀)"
  printf 'set $upstream %s:3000;\n' "$CUR_SVC" > "$ACTIVE_FILE"
  docker compose exec -T "$NGINX_SVC" nginx -s reload
  # shellcheck disable=SC2086
  docker compose $NEXT_PROFILE rm -sf "$NEXT_SVC" || true
  err "롤백 완료. $CURRENT 가 다시 활성."
  exit 1
fi
log "✅ 스모크 테스트 통과"

# ── 7) 이전 색 종료 ───────────────────────────────────────────
log "이전 색 $CUR_SVC 종료"
# shellcheck disable=SC2086
docker compose $CUR_PROFILE rm -sf "$CUR_SVC" || true

log "🎉 무중단 배포 성공: $CURRENT → $NEXT"

3.8 수동 배포·롤백

CI 가 막혔을 때 손으로 같은 순서를 밟는 방법. 배포는 pull + up, 롤백은 start 라는 구분이 핵심이다.

수동 배포 / 롤백 (blue → green 예시) 
cd /srv/app

# 현재 활성 색 확인
cat nginx/active/upstream.conf        # set $upstream backend_green:3000; → green 활성

# ── 배포: green 활성 → blue 로 올리기 ────────────────────────
docker compose pull backend_blue      # ★ 이걸 빼면 캐시된 옛 이미지가 그대로 뜬다
docker compose up -d backend_blue
docker compose ps                     # backend_blue 가 전부 (healthy) 될 때까지 대기

# 헬스체크가 안 되면 여기서 취소한다 (green 은 계속 서비스 중이므로 영향 없음)
#   docker compose rm -sf backend_blue

echo 'set $upstream backend_blue:3000;' > nginx/active/upstream.conf
docker compose exec nginx nginx -s reload
curl -fsS http://localhost:8080/health          # 스모크 테스트
docker compose --profile green stop backend_green

# ── 롤백: blue 활성 → green 으로 복귀 ────────────────────────
# ★ pull/up 이 아니라 start. 옛 이미지로 만들어진 컨테이너를 그대로 되살린다.
docker compose --profile green start backend_green
docker compose --profile green ps               # (healthy) 대기
echo 'set $upstream backend_green:3000;' > nginx/active/upstream.conf
docker compose exec nginx nginx -s reload
curl -fsS http://localhost:8080/health
docker compose stop backend_blue

docker compose pull 을 빼먹으면 캐시된 옛 이미지가 그대로 다시 뜬다. 헬스체크와 스모크 테스트는 통과하므로 "배포 성공" 으로 보이지만 코드는 바뀌지 않는다.

4. PM2 배포 PM2

docker 판과 단계가 1:1로 대응한다. 다른 점은 세 가지다: 색이 컨테이너가 아니라 포트로 갈리고, 코드 격리를 릴리스 디렉터리로 하고, nginx 가 호스트에 있어 조작에 sudo 가 필요하다.

4.2 배포 워크플로

.github/workflows/deploy-pm2.yml 
name: Build and Deploy (pm2)

# main 에 push(=PR 머지) 될 때마다 번들을 만들어 운영 서버에 blue-green 배포
on:
  push:
    branches: [main]
  workflow_dispatch: # 필요 시 수동 실행

# 배포 도중 새 push 로 workflow 가 취소되면 blue-green 전환이 중간에 끊길 수 있다.
# 같은 브랜치의 실행은 취소하지 않고 순서대로 대기시킨다.
concurrency:
  group: build-and-deploy-${{ github.ref }}
  cancel-in-progress: false

jobs:
  # ── 1) 버전 태그 중복 검사 ─────────────────────────────
  # 이미지 레지스트리가 없으므로 git tag 로 같은 판정을 한다.
  # package.json 의 version 태그가 이미 있으면 실패 → 아래 잡이 안 돎
  check-version:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    outputs:
      version: ${{ steps.pkg.outputs.version }}
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0 # 태그 조회용

      - name: Read version from package.json
        id: pkg
        run: echo "version=$(node -p "require('./package.json').version")" >> "$GITHUB_OUTPUT"

      - name: Fail if version tag already exists
        run: |
          TAG="v${{ steps.pkg.outputs.version }}"
          if git ls-remote --exit-code --tags origin "refs/tags/$TAG" >/dev/null 2>&1; then
            echo "::error::$TAG 태그가 이미 존재 — package.json version 을 올리세요."
            exit 1
          fi
          echo "$TAG 없음 → 빌드 진행"

  # ── 2) 번들 빌드 ───────────────────────────────────────
  build:
    needs: check-version
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      # Prisma Client 생성에는 URL 형식이 필요하지만 DB 연결은 하지 않는다.
      DATABASE_URL: mysql://ci:ci@localhost:3306/ci

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Generate Prisma Client
        run: npx prisma generate

      - name: Build
        run: npm run build

      # ★ node_modules 와 prisma/generated 는 넣지 않는다.
      #   네이티브 모듈(sharp)·Prisma 쿼리 엔진은 플랫폼(arm64/x64, glibc/musl)에 묶여 있어
      #   러너에서 만든 것을 운영 서버에 그대로 옮기면 실행 시점에 깨진다. 서버에서 다시 만든다.
      - name: Pack release artifact
        run: |
          tar -czf release.tar.gz \
            dist package.json package-lock.json prisma ecosystem.config.js public

      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: release
          path: release.tar.gz
          retention-days: 7

  # ── 3) 운영 서버 배포 ──────────────────────────────────
  deploy:
    needs: [check-version, build]
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: write # 성공 후 버전 태그 push

    steps:
      # 배포 스크립트를 보내기 위해 다시 checkout 한다.
      - name: Checkout
        uses: actions/checkout@v4

      - name: Download artifact
        uses: actions/download-artifact@v4
        with:
          name: release

      # 운영 환경변수는 저장소에 두지 않고 production Environment Secret 으로 파일을 만든다.
      - name: Create deployment environment file
        env:
          PROD_ENV_FILE: ${{ secrets.PROD_ENV_FILE }}
        run: |
          if [ -z "$PROD_ENV_FILE" ]; then
            echo "::error::production Environment Secret PROD_ENV_FILE 이 비어 있습니다."
            exit 1
          fi
          umask 077
          printf '%s\n' "$PROD_ENV_FILE" > .env.deploy

      - name: Upload release to server
        uses: appleboy/scp-action@v1
        with:
          host: ${{ secrets.PROD_SSH_HOST }}
          port: ${{ secrets.PROD_SSH_PORT }}
          username: ${{ secrets.PROD_SSH_USER }}
          key: ${{ secrets.PROD_SSH_PRIVATE_KEY }}
          fingerprint: ${{ secrets.PROD_SSH_FINGERPRINT }}
          source: release.tar.gz,.env.deploy,scripts/deploy-pm2.sh
          target: ${{ vars.PROD_DEPLOY_PATH }}/incoming
          overwrite: true

      - name: Deploy over SSH
        uses: appleboy/ssh-action@v1.2.2
        env:
          DEPLOY_PATH: ${{ vars.PROD_DEPLOY_PATH }}
          RELEASE: v${{ needs.check-version.outputs.version }}-${{ github.sha }}
        with:
          host: ${{ secrets.PROD_SSH_HOST }}
          port: ${{ secrets.PROD_SSH_PORT }}
          username: ${{ secrets.PROD_SSH_USER }}
          key: ${{ secrets.PROD_SSH_PRIVATE_KEY }}
          fingerprint: ${{ secrets.PROD_SSH_FINGERPRINT }}
          envs: DEPLOY_PATH,RELEASE
          script: |
            set -euo pipefail
            chmod 600 "${DEPLOY_PATH}/incoming/.env.deploy"
            chmod +x "${DEPLOY_PATH}/incoming/scripts/deploy-pm2.sh"
            "${DEPLOY_PATH}/incoming/scripts/deploy-pm2.sh"

      # 배포가 성공한 커밋에만 태그를 남긴다 → 다음 배포의 중복 검사 기준이 된다.
      - name: Tag released version
        run: |
          TAG="v${{ needs.check-version.outputs.version }}"
          git tag "$TAG"
          git push origin "$TAG"

node_modules 를 아티팩트에 넣지 말 것. sharp 같은 네이티브 모듈과 Prisma 쿼리 엔진은 아키텍처(arm64/x64)와 libc(glibc/musl)에 묶인 바이너리를 포함한다. 러너에서 만든 것을 서버로 옮기면 설치는 성공하고 실행 시점에 깨진다.

  kill_timeout: 30000,

      env: { NODE_ENV: 'prod', PORT: 3001 },

4.4 nginx 설정

/etc/nginx/conf.d/app.conf 
# /etc/nginx/conf.d/app.conf
#
# docker 판과 다른 점: 백엔드가 호스트 프로세스이므로 컨테이너 DNS(resolver)가 필요 없고,
# upstream 블록을 쓸 수 있어 keepalive 로 커넥션을 재사용할 수 있다.

map $http_x_forwarded_proto $forwarded_proto {
    default $http_x_forwarded_proto;
    ''      $scheme;
}

log_format json_log escape=json '{'
    '"req_id":"$request_id",'
    '"method":"$request_method",'
    '"url":"$request_uri",'
    '"status":"$status",'
    '"target":"$upstream",'
    '"upstream_addr":"$upstream_addr",'
    '"upstream_status":"$upstream_status",'
    '"request_time":"$request_time",'
    '"upstream_time":"$upstream_response_time",'
    '"body_bytes":"$body_bytes_sent",'
    '"ip":"$remote_addr",'
    '"ua":"$http_user_agent"'
'}';

# 색별 포트는 ecosystem.config.js 와 반드시 일치해야 한다.
upstream app_blue  { server 127.0.0.1:3001; keepalive 32; }
upstream app_green { server 127.0.0.1:3002; keepalive 32; }

server {
    listen 80;
    server_name _;

    access_log /var/log/nginx/access.log json_log;
    client_max_body_size 6m;

    location / {
        # set $upstream app_blue;  ← 배포 스크립트가 이 한 줄만 바꾼다
        include /etc/nginx/app-active/upstream.conf;
        # proxy_pass 에 변수를 쓰면서 그 값이 upstream 블록 이름이면 resolver 없이 그 그룹으로 간다.
        proxy_pass http://$upstream;
        proxy_http_version 1.1;
        # keepalive 를 쓰려면 hop-by-hop Connection 헤더를 비워야 한다.
        proxy_set_header Connection "";

        proxy_connect_timeout 5;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $forwarded_proto;
        proxy_set_header X-Request-Id      $request_id;
    }
}

4.5 배포 스크립트

scripts/deploy-pm2.sh 
#!/usr/bin/env bash
# ─────────────────────────────────────────────────────────────
# pm2 Blue-Green 무중단 배포 스크립트 (운영 서버에서 실행)
#
# 흐름: docker 판(scripts/deploy.sh)과 단계가 동일하다.
#   0) 릴리스 전개 + 의존성 설치
#   1) 현재 활성 색 파악 (nginx active/upstream.conf 에서 읽음)
#   2) 반대 색을 새 릴리스로 기동
#   3) 새 색 헬스체크 (★ 전환 전에!)
#        실패 → 새 색 삭제, 배포 취소 (현재 색 무사 = 사용자 영향 0)
#   4) upstream.conf 를 새 색으로 교체
#   5) nginx reload (graceful = 무중단 전환)
#   6) 스모크 테스트 (nginx 통해 실제 200 응답 확인)
#        실패 → upstream 롤백 + reload, 새 색 삭제
#   7) 이전 색 stop (삭제하지 않음 = 빠른 롤백 위해 보존)
#
# 전제:
#   - CI 가 $APP_ROOT/incoming/ 에 release.tar.gz, .env.deploy 를 올린 뒤 이 스크립트를 호출
#   - 호스트 nginx 가 $ACTIVE_FILE 을 include (가이드 4.4)
#   - nginx 조작용 sudoers NOPASSWD 설정 완료 (가이드 4.6)
# ─────────────────────────────────────────────────────────────
set -euo pipefail

INCOMING="$(cd "$(dirname "$0")/.." && pwd)"   # $APP_ROOT/incoming
APP_ROOT="$(dirname "$INCOMING")"
RELEASES="$APP_ROOT/releases"
SHARED="$APP_ROOT/shared"
ACTIVE_FILE="/etc/nginx/app-active/upstream.conf"

RELEASE="${RELEASE:-manual-$(date +%Y%m%d%H%M%S)}"
KEEP_RELEASES=5        # 남겨둘 과거 릴리스 개수
HEALTH_TIMEOUT=90      # 새 색 헬스체크 최대 대기(초)
POLL_INTERVAL=3        # 헬스체크 폴링 간격(초)
BLUE_PORT=3001
GREEN_PORT=3002
SMOKE_URL="http://127.0.0.1/health"   # nginx 를 통과하는 경로여야 의미가 있다

log()  { printf '\033[1;34m[deploy]\033[0m %s\n' "$*"; }
err()  { printf '\033[1;31m[deploy:error]\033[0m %s\n' "$*" >&2; }

port_of() { [ "$1" = "green" ] && echo "$GREEN_PORT" || echo "$BLUE_PORT"; }

set_upstream() {
  printf 'set $upstream app_%s;\n' "$1" | sudo tee "$ACTIVE_FILE" >/dev/null
}

# 지정 포트가 200 을 돌려줄 때까지 기다린다.
wait_for_health() {
  local port="$1" elapsed=0
  log "127.0.0.1:${port}/health 헬스체크 대기 (최대 ${HEALTH_TIMEOUT}s)..."
  while :; do
    if curl -fsS -m 3 "http://127.0.0.1:${port}/health" >/dev/null 2>&1; then
      log "✅ 포트 ${port} healthy"
      return 0
    fi
    if [ "$elapsed" -ge "$HEALTH_TIMEOUT" ]; then
      err "포트 ${port} 헬스체크 실패"
      return 1
    fi
    sleep "$POLL_INTERVAL"
    elapsed=$((elapsed + POLL_INTERVAL))
  done
}

# ── 0) 릴리스 전개 ────────────────────────────────────────────
RELEASE_DIR="$RELEASES/$RELEASE"
log "릴리스 전개: $RELEASE_DIR"
mkdir -p "$RELEASES" "$SHARED"
rm -rf "$RELEASE_DIR"
mkdir -p "$RELEASE_DIR"
tar -xzf "$INCOMING/release.tar.gz" -C "$RELEASE_DIR"

# 앱이 dotenv/config 로 cwd 의 .env 를 읽으므로 릴리스마다 심볼릭 링크한다.
install -m 600 "$INCOMING/.env.deploy" "$SHARED/.env"
ln -sfn "$SHARED/.env" "$RELEASE_DIR/.env"

cd "$RELEASE_DIR"
# prisma CLI 가 devDependency 이므로 전체 설치 → generate → dev 제거 순서로 한다.
# (--omit=dev 로 먼저 깔면 prisma generate 가 CLI 를 못 찾는다)
log "의존성 설치 + Prisma Client 생성"
npm ci
npx prisma generate
npm prune --omit=dev

# ── 1) 현재 활성 색 파악 ──────────────────────────────────────
if [ ! -f "$ACTIVE_FILE" ]; then
  err "$ACTIVE_FILE 가 없습니다. 서버 최초 세팅을 먼저 수행하세요."
  exit 1
fi

if grep -q app_green "$ACTIVE_FILE"; then
  CURRENT=green; NEXT=blue
else
  CURRENT=blue;  NEXT=green
fi
CUR_PORT=$(port_of "$CURRENT")
NEXT_PORT=$(port_of "$NEXT")

log "현재 활성: $CURRENT($CUR_PORT)  →  새로 배포: $NEXT($NEXT_PORT)"

# ── 2) 새 색 기동 ─────────────────────────────────────────────
# 같은 이름의 옛 프로세스는 옛 릴리스 디렉터리를 cwd 로 물고 있으므로 지우고 새로 올린다.
# (pm2 restart 는 cwd 를 바꾸지 않아 새 코드가 반영되지 않는다)
log "app-$NEXT 기동 (cwd=$RELEASE_DIR)"
pm2 delete "app-$NEXT" >/dev/null 2>&1 || true
pm2 start ecosystem.config.js --only "app-$NEXT"

# ── 3) 새 색 헬스체크 (전환 전!) ──────────────────────────────
if ! wait_for_health "$NEXT_PORT"; then
  err "app-$NEXT 헬스체크 실패 → 배포 취소 (현재 색 $CURRENT 무사)"
  pm2 logs "app-$NEXT" --lines 50 --nostream || true
  pm2 delete "app-$NEXT" >/dev/null 2>&1 || true
  exit 1
fi

# ── 4) upstream 전환 ──────────────────────────────────────────
log "upstream → app_$NEXT 로 전환"
set_upstream "$NEXT"

# ── 5) nginx reload (무중단) ──────────────────────────────────
log "nginx reload (graceful)"
sudo nginx -t
sudo nginx -s reload
sleep 1

# ── 6) 스모크 테스트 ──────────────────────────────────────────
log "스모크 테스트 ($SMOKE_URL)..."
if ! curl -fsS -m 5 "$SMOKE_URL" >/dev/null; then
  err "스모크 테스트 실패 → 롤백 ($CURRENT 로 복귀)"
  set_upstream "$CURRENT"
  sudo nginx -s reload
  pm2 delete "app-$NEXT" >/dev/null 2>&1 || true
  err "롤백 완료. $CURRENT 가 다시 활성."
  exit 1
fi
log "✅ 스모크 테스트 통과"

# ── 7) 이전 색 정지 ───────────────────────────────────────────
# delete 가 아니라 stop → 롤백 때 start 만으로 옛 코드가 그대로 돌아온다.
log "이전 색 app-$CURRENT 정지"
pm2 stop "app-$CURRENT" >/dev/null 2>&1 || true
# 재부팅 후 pm2-startup 이 되살릴 목록을 갱신한다.
pm2 save

# ── 8) 오래된 릴리스 정리 ─────────────────────────────────────
# 정지된 이전 색이 아직 옛 릴리스를 cwd 로 쓰므로 KEEP_RELEASES 는 2 이상이어야 한다.
cd "$RELEASES"
ls -1dt */ 2>/dev/null | tail -n "+$((KEEP_RELEASES + 1))" | xargs -r rm -rf

log "🎉 무중단 배포 성공: $CURRENT → $NEXT ($RELEASE)"

4.8 pm2 reload 로 충분한 경우

pm2 는 pm2 reload 로 cluster 워커를 하나씩 교체하는 자체 무중단 기능이 있다. blue-green 없이 이것만 쓰는 것은 다음 조건을 모두 만족할 때만 허용한다.

  • 새 코드가 기동에 실패해도 즉시 알아차릴 수 있다 (reload 는 실패한 워커를 계속 재시작하며 옛 워커를 이미 죽였을 수 있다)
  • 롤백을 재배포로 감당할 수 있다 (직전 버전이 서버에 없다)
  • DB 마이그레이션이 없거나 하위 호환이다

reload 는 전환 전 헬스체크와 즉시 롤백을 제공하지 못한다. 그래서 사내 표준은 blue-green 이고, reload 는 내부 도구·배치처럼 장애 허용도가 높은 것에만 쓴다.
