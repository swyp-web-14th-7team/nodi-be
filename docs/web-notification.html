nodi 실시간 알림 설계 문서

연결 요청 수락 · 거절 알림의 실시간 전달(SSE) 구현 계획 — 프론트엔드 · 백엔드 역할 분리

작성일 2026-07-29 · 백엔드 nodi-be (NestJS 11 / Prisma 7 / MariaDB / Redis / nginx, 인스턴스 2대) · 프론트엔드 Vite + React (JavaScript)

1. 개요

사용자가 서비스를 사용 중일 때 자신이 보낸 연결 요청의 처리 결과를 새로고침 없이 즉시 전달한다. 브라우저가 닫힌 상태에서의 전달(Web Push)은 10장에서 확장 계획으로만 다룬다.

1.1 알림 대상 이벤트

현재 범위의 알림은 두 가지뿐이다. 두 경우 모두 CardConnectionRequest의 요청자(requesterCard.userId)에게 전달된다. 수신자(응답한 사람)에게는 알림을 보내지 않는다. 본인이 방금 누른 행동이기 때문이다.

타입발생 지점수신자토스트이동 경로
CONNECTION_ACCEPTED (1) ConnectionRequestsService.acceptRequest() 요청자 노출 보관함 (성립된 CardConnection)
CONNECTION_REJECTED (2) ConnectionRequestsService.rejectRequest() 요청자 노출 보낸 요청 목록

알림 타입이 곧 토스트 대상 전부이므로 타입별 노출 분기 로직이 필요 없다. 단, 재연결 시 목록을 다시 불러올 때 과거 알림이 토스트로 쏟아지지 않도록 토스트는 SSE 이벤트 수신 경로에서만 띄운다 (6.4).

1.2 기술 선택

방식앱 종료 시 전달프론트 작업량서버 부담판정
SSE (Server-Sent Events) 불가 낮음 — 라이브러리 1개 (fetch-event-source) 커넥션 유지 (경량) 채택
WebSocket 불가 중간 — socket.io-client, 재연결/인증 직접 처리 커넥션 유지 보류 — 양방향 통신 요구 없음
Web Push (VAPID) 가능 높음 — Service Worker, 권한 UX, 구독 관리 낮음 (벤더 위임) 2단계 확장
폴링 불가 낮음 높음 (트래픽 낭비) 미채택

서버→클라이언트 단방향 전송만 필요하고, NestJS가 @Sse()를 내장하며, 기존 AuthGuard·Pipe·Filter가 그대로 적용된다. WebSocket처럼 게이트웨이·어댑터· 별도 포트·핸드셰이크가 필요 없다.

인증 방식 때문에 브라우저 내장 EventSource는 쓸 수 없다. 이 프로젝트의 auth.guard.ts:75-78은 Authorization: Bearer 헤더만 읽는데, EventSource는 커스텀 헤더를 붙일 수 없다(브라우저 명세). 쿠키에는 리프레시 토큰과 device_id만 들어 있고 액세스 토큰은 응답 바디로 나가므로 withCredentials로도 인증이 통과하지 않는다. 따라서 프론트는 @microsoft/fetch-event-source를 쓴다 (6.1). 백엔드 인증 코드는 변경하지 않는다.

3.3 로그아웃

프론트가 es.close()로 스트림을 닫고 알림 상태를 비운다. 상태를 비우지 않으면 다음 로그인 사용자에게 이전 사용자의 알림이 노출된다. 백엔드는 커넥션 종료 이벤트에서 Redis 구독을 해제한다.

3.4 커넥션 회수 — 언제, 어떻게 정리되는가

SSE는 장수명 커넥션이라 "클라이언트가 사라졌을 때 서버가 그것을 언제 아는가"가 리소스 관리의 핵심이다. 정상 종료와 비정상 종료의 동작이 완전히 다르다.

정상 경로 — 즉시 회수

탭 닫기 / 브라우저 종료 / es.close()
  → 브라우저(또는 OS)가 TCP FIN 전송
  → nginx가 클라이언트 연결 종료 감지
  → nginx가 upstream(Node) 연결도 끊음   (proxy_ignore_client_abort off = 기본값)
  → Node의 req 'close' 이벤트
  → Nest가 @Sse() Observable 구독 해제
  → finalize() 실행 → Redis unsubscribe

브라우저 프로세스를 강제 종료해도 OS가 대신 FIN/RST를 보내므로 결과는 같다. 이 경로는 추가 코드 없이 동작한다. 5.4의 finalize()가 여기에 걸려 있다.

비정상 경로 — 신호가 오지 않는 경우

랜선 뽑기, 와이파이 이탈, 절전 모드, 지하철 진입. 기계나 네트워크 경로 자체가 사라지면 FIN이 오지 않는다. 서버는 커넥션이 살아있다고 믿고 계속 붙잡는다. 정리되는 유일한 계기는 다음 쓰기 시도가 실패하는 것이며, 여기서 heartbeat가 작동한다. 

t=0       클라이언트 소멸 (신호 없음)
t=20초    nginx가 heartbeat write() → 커널 송신 버퍼에 적재, 성공 반환
          커널이 패킷 전송 → ACK 없음
t=20초~   커널이 지수 백오프로 재전송 (0.2s → 0.4s → … → 120s 상한 반복)
t=약 15분  tcp_retries2(기본 15회) 소진 → 소켓 ETIMEDOUT
          nginx가 클라이언트·upstream 연결 종료 → finalize() → Redis unsubscribe

송신 버퍼가 차서 죽는 것이 아니다. heartbeat는 15바이트 남짓이고 리눅스 기본 송신 버퍼는 16KB 이상이라, 버퍼가 차려면 16384 ÷ 15 × 20초 ≈ 6시간이 걸린다. 그 전에 TCP 재전송 소진(약 15분)이 먼저 커넥션을 끝낸다.

heartbeat의 이중 역할

20초 heartbeat는 프록시 유휴 타임아웃 방지용으로만 넣은 것이 아니다. 재전송 타이머를 시작시키는 트리거이기도 하다. 서버가 아무것도 쓰지 않으면 커널은 상대가 죽었는지 알 방법이 없다 — TCP는 침묵을 이상하게 여기지 않는다. 그 상태로 방치되면 tcp_keepalive_time(기본 7200초 = 2시간)이 돌 때까지 커넥션이 남는다. heartbeat를 끄면 이 회수 메커니즘 자체가 사라진다.

감지 주체는 nginx다. 죽은 구간은 클라이언트↔nginx이고 Node가 보는 상대는 nginx다. 따라서 Node 쪽에 socket.setKeepAlive()를 걸어도 소용없다. nginx가 클라이언트로 heartbeat를 흘려보내다 실패하면서 upstream을 끊어줘야 비로소 Node의 finalize가 돈다.

회수 시점 요약

튜닝하지 않는다

tcp_retries2는 시스템 전역 설정이라 낮추면 일반 API 커넥션까지 영향을 받는다. 불안정한 모바일 환경에서 정상 요청이 끊길 수 있어 권하지 않는다. 인스턴스 2대 규모에서 15분짜리 좀비 커넥션 수십 개는 실질적 부담이 아니다. 필요한 것은 코드가 아니라 관측이다. 

# 인스턴스별 실제 소켓 수
ss -tn state established '( sport = :3000 )' | wc -l

# Redis 구독 채널 수 — 이것만 단조 증가하면 좀비가 아니라 finalize 누락(코드 버그)
redis-cli PUBSUB CHANNELS 'noti:*' | wc -l

두 수치가 접속 중인 사용자 수와 대략 비례하면 정상이다. 운영 환경에서는 매번 셸에 붙지 않고 8장의 sse_stats 로깅으로 Grafana에서 추세를 본다.

       "requestId":"01J8ZA...","connectionId":"01J8ZB...",
       "counterpartCardId":"01J8ZC...","counterpartName":"김노디",

event: ping
data:
  • type은 1 = ACCEPTED, 2 = REJECTED. 표시 문구는 프론트가 조립한다 (서버가 문장을 들고 있으면 카피 수정 때마다 배포가 필요하다).
  • connectionId는 수락일 때만 존재. 토스트/알림 클릭 시 보관함 상세로 이동하는 데 쓴다.
  • event: ping은 20초 주기 heartbeat다. 프론트에 ping 리스너가 없으므로 브라우저가 디스패치 후 그냥 버린다 (6.6). 역할은 3.4 참고.

SSE 주석 프레임(: heartbeat)이 아니라 이름 붙은 이벤트다. NestJS @Sse()는 MessageEvent 객체를 직렬화하는 방식이라 id / event / data / retry 필드만 쓸 수 있고, 콜론 주석 프레임은 표현할 수 없다. 굳이 주석 프레임을 보내려면 @Res()로 응답 객체를 직접 잡아야 하는데 그럴 이유가 없다 — 기능적 차이는 없다.

pub/sub을 lib에 두는 이유

현재 lib/redis/redis.service.ts는 클라이언트 1개를 private로 감싸고 get / set / del만 노출한다. pub/sub이 없고 원본 클라이언트를 꺼낼 수도 없다. 그렇다고 module/notifications/에서 new Redis(...)를 하면 연결 설정이 두 군데로 갈라진다 — redis.service.ts:15-19의 host · port · username · password 읽는 코드를 복사하게 되고, 나중에 TLS나 재시도 정책을 추가할 때 한쪽만 고치는 사고가 난다.

그리고 pub/sub 커넥션은 성격상 기존 RedisService와 합칠 수 없다. subscribe 모드에 들어간 커넥션은 get / set이 거부되기 때문이다. 이 제약은 클래스를 나눠야 하는 이유이지, 도메인 쪽으로 밀어낼 이유가 아니다.

// src/module/notifications/notifications.controller.ts

      // heartbeat — `event: ping` 프레임으로 나간다. 프록시 유휴 타임아웃 방지 +
      // 죽은 커넥션 탐지 트리거 두 역할을 겸한다 (3.4 참고). 끄면 안 된다.
      interval(20_000).pipe(map(() => ({ type: 'ping', data: '' }))),
    ).pipe(
      // 토큰은 연결 시점에 1회만 검증된다. 상한이 없으면 액세스 토큰이 만료된 뒤에도
      // 스트림이 몇 시간씩 살아남는다. 주기적으로 끊어 재인증을 강제한다.
      takeUntil(timer(30 * 60 * 1000)),
    );
  }
}

스트림 수명을 제한하는 이유. AuthGuard는 연결을 맺는 순간 한 번만 토큰을 검증한다. SSE는 응답이 끝나지 않는 요청이므로, 상한이 없으면 액세스 토큰이 만료되고 심지어 계정이 정지되어도 그 커넥션은 계속 알림을 받는다. 30분마다 서버가 스트림을 complete하면 클라이언트가 재연결하면서 새 토큰으로 다시 인증받는다. 프론트 입장에서는 onerror → 재시도 경로라 6.1 코드에 추가 처리가 필요 없다.

게이트웨이도 어댑터도 별도 포트도 필요 없다. SSE는 평범한 HTTP 응답이라 기존 AuthGuard · Pipe · Filter가 그대로 적용된다. 그런데 바로 그 "그대로 적용된다"가 문제를 일으킨다.

5.4 Redis Pub/Sub 인스턴스 2대 필수

인스턴스가 2대이므로 수락을 처리한 서버와 요청자의 SSE 커넥션을 쥔 서버가 다를 확률이 약 50%다. 인메모리 Subject만 쓰면 절반의 알림이 실시간으로 도달하지 않는다. Redis Pub/Sub이 이 간극을 메운다. ioredis가 이미 의존성에 있다.

lib/redis/redis-pubsub.service.ts — 인프라

@Injectable()
export class RedisPubSubService implements OnModuleInit, OnModuleDestroy {
  private readonly sub: Redis;
  private readonly pub: Redis;
  private readonly channels = new Map<string, Subject<string>>();

  constructor(
    configService: ConfigService,
    @InjectPinoLogger(RedisPubSubService.name)
    private readonly logger: PinoLogger,
  ) {
    // redis.config.ts 의 옵션 팩토리를 RedisService 와 공유한다
    this.sub = new Redis(buildRedisOptions(configService));
    this.pub = new Redis(buildRedisOptions(configService));

    // ★ 핸들러가 없으면 ioredis 의 error 가 unhandled 로 프로세스를 죽인다
    this.sub.on('error', (e) => this.logger.error(`sub: ${e.message}`));
    this.pub.on('error', (e) => this.logger.error(`pub: ${e.message}`));

    this.sub.on('message', (channel, raw) => {
      this.channels.get(channel)?.next(raw);
    });
  }

  async onModuleInit() {
    await Promise.all([this.sub.connect(), this.pub.connect()]);
  }

  /** 채널 구독. 구독자가 모두 떠나면 자동으로 UNSUBSCRIBE 한다. */
  subscribe(channel: string): Observable<string> {
    let subject = this.channels.get(channel);
    if (!subject) {
      subject = new Subject<string>();
      this.channels.set(channel, subject);
      void this.sub.subscribe(channel);
    }
    return subject.asObservable().pipe(
      finalize(() => {                       // 커넥션 종료 시 정리
        if (!subject.observed) {             // 같은 유저의 다른 탭이 없을 때만
          this.channels.delete(channel);
          void this.sub.unsubscribe(channel);
        }
      }),
    );
  }

  async publish(channel: string, message: string) {
    await this.pub.publish(channel, message);
  }

  /** 8.1 sse_stats 용. sub 은 subscribe 모드라 명령이 거부되므로 pub 으로 조회. */
  async countChannels(pattern: string): Promise<number> {
    const channels = await this.pub.pubsub('CHANNELS', pattern);
    return channels.length;
  }

  /** 로컬 구독 수 — Redis 왕복 없이 이 인스턴스의 상태만 본다. */
  get localChannelCount(): number {
    return this.channels.size;
  }

  async onModuleDestroy() {
    await Promise.allSettled([this.sub.quit(), this.pub.quit()]);
  }
}

Redis 커넥션은 반드시 분리한다. subscribe 모드에 들어간 커넥션은 일반 명령을 받지 못한다. 기존 RedisService의 캐시용 클라이언트를 재사용하면 get / set이 전부 깨진다. lazyConnect: true + onModuleInit 연결, error 핸들러 등록, @InjectPinoLogger 로거 주입은 기존 redis.service.ts의 패턴을 그대로 따른 것이다.

5.6 nginx 설정

기본 설정 그대로면 nginx가 응답을 버퍼링해서 이벤트가 실시간으로 나가지 않는다.

location /api/notifications/stream {
    proxy_pass http://nodi_be;
    proxy_http_version 1.1;

    proxy_buffering off;          # 필수 — 없으면 이벤트가 버퍼에 갇힌다
    proxy_cache off;
    proxy_set_header Connection '';
    proxy_read_timeout 3600s;     # heartbeat 가 멈췄을 때를 대비한 안전장치
    chunked_transfer_encoding off;

    access_log off;               # 장수명 요청이 로그를 오염시킨다
}

proxy_read_timeout은 기본값(60초)으로도 당장은 끊기지 않는다. 이 값은 upstream으로부터의 연속된 두 읽기 사이 간격이라, 20초 heartbeat가 계속 타이머를 리셋하기 때문이다. 그래도 명시하는 이유는 heartbeat가 멈추거나 주기를 늘리는 변경이 있을 때 조용히 끊기는 것을 막기 위해서다. 진짜 필수는 proxy_buffering off 하나다 — 이건 없으면 즉시 깨진다.

nginx/conf.d/default.conf의 기존 location /에는 proxy_next_upstream error timeout …이 설정되어 있는데, 이 지시어는 응답 헤더를 받기 전에만 동작하므로 스트림 도중 재시도가 발생하지는 않는다. 다만 위 전용 location을 location /보다 먼저 두어야 매칭이 우선한다.

스트림은 어느 인스턴스에 붙어도 되므로 sticky session 설정은 불필요하다. Redis Pub/Sub이 인스턴스 위치를 무의미하게 만드는 것이 이 설계의 핵심 이점이다.

src/contexts/NotificationContext.jsx

import { createContext, useContext, useState, useEffect, useMemo, useCallback } from 'react';
import { fetchEventSource } from '@microsoft/fetch-event-source';
import { useAuth } from './AuthContext';
import { fetchNotifications } from '../api/notifications';
import { toast } from '../lib/toast';

const NotificationContext = createContext(null);

export function NotificationProvider({ children }) {
  const { isLoggedIn, getAccessToken, refreshAccessToken } = useAuth();
  const [items, setItems] = useState([]);
  const [retryKey, setRetryKey] = useState(0);   // 토큰 갱신 후 재연결 트리거

  // 목록 API로 상태를 덮어쓴다. 토스트는 띄우지 않는다.
  const syncFromServer = useCallback(async () => {
    try {
      const { items } = await fetchNotifications({ limit: 20 });
      setItems(items);
    } catch (e) {
      console.error('[noti] 목록 동기화 실패', e);
    }
  }, []);

  useEffect(() => {
    if (!isLoggedIn) {
      setItems([]);              // 로그아웃 시 이전 사용자 알림 제거
      return;
    }

    const ctrl = new AbortController();

    void fetchEventSource('/api/notifications/stream', {
      signal: ctrl.signal,
      headers: { Authorization: `Bearer ${getAccessToken()}` },

      // 기본값(false)이면 탭이 백그라운드로 가는 순간 커넥션을 닫는다.
      // 다른 탭을 보는 동안에도 알림을 받아야 하므로 true.
      openWhenHidden: true,

      // 최초 연결 + 재연결 모두 여기를 지난다 → 단절 구간 누락 보정
      async onopen(res) {
        if (res.ok) { void syncFromServer(); return; }
        // throw = 재시도 중단. 401 은 재시도해도 계속 실패한다.
        if (res.status === 401) throw new AuthExpiredError();
        throw new Error(`stream failed: ${res.status}`);
      },

      // ★ EventSource 와 달리 이벤트별 리스너가 없다. 모든 프레임이 여기로 온다.
      onmessage(ev) {
        if (ev.event !== 'notification') return;   // ping 등은 버린다
        const noti = JSON.parse(ev.data);
        setItems((prev) => {
          if (prev.some((p) => p.id === noti.id)) return prev;   // 중복 방지
          showToast(noti);                                        // 실시간 수신에만 토스트
          return [noti, ...prev];
        });
      },

      onerror(err) {
        if (err instanceof AuthExpiredError) {
          void refreshAccessToken().then(() => setRetryKey((k) => k + 1));
          throw err;              // 이 스트림은 중단, 새 토큰으로 다시 연다
        }
        return 3000;              // 숫자 반환 = 해당 ms 후 재시도
      },
    });

    return () => ctrl.abort();
  }, [isLoggedIn, retryKey, syncFromServer]);

  const value = useMemo(
    () => ({
      items,
      unread: items.filter((i) => !i.readAt).length,
      refresh: syncFromServer,
    }),
    [items, syncFromServer],
  );

  return (
    <NotificationContext.Provider value={value}>
      {children}
    </NotificationContext.Provider>
  );
}

export function useNotifications() {
  const ctx = useContext(NotificationContext);

6.6 heartbeat 처리

서버가 20초마다 event: ping을 보낸다. fetch-event-source는 이벤트별 리스너가 없고 모든 프레임이 onmessage 하나로 들어오므로, 프론트에서 반드시 걸러야 한다. 브라우저 내장 EventSource였다면 리스너가 없어 자동으로 버려졌겠지만 여기서는 아니다. 

onmessage(ev) {
  if (ev.event !== 'notification') return;   // ★ 이 줄이 없으면 ping 이 알림으로 처리된다
  const noti = JSON.parse(ev.data);          // ping 의 data 는 '' → JSON.parse 에서 throw
  ...
}

이 필터를 빠뜨리면 20초마다 JSON.parse('')가 예외를 던진다. onmessage 안에서 던진 예외는 fetch-event-source가 onerror로 넘기고, onerror가 숫자를 반환하면 재연결한다. 결과적으로 20초마다 커넥션이 재수립되는 루프에 빠지는데, 화면상으로는 "가끔 알림이 늦게 온다" 정도로만 보여 원인을 찾기 어렵다. 이벤트 이름으로 거르는 것을 onmessage의 첫 줄로 두는 이유다.

선택: watchdog (초기 구현에서는 제외)

heartbeat를 더 적극적으로 쓴다면 용도는 하나 — 서버 방향의 조용한 죽음을 감지하는 것이다. 3.4에서 다룬 문제의 거울상으로, 중간 방화벽이 커넥션을 조용히 끊거나 서버가 비정상 종료되면 클라이언트도 즉시 알지 못한다. 이벤트도 에러도 없는 상태로 몇 분간 죽어 있을 수 있고, 그동안 재연결은 발동하지 않는다. 

let watchdog;
const kick = () => {
  clearTimeout(watchdog);
  watchdog = setTimeout(() => {
    ctrl.abort();                 // 강제로 끊고
    setRetryKey((k) => k + 1);    // effect 재실행 → 재연결
  }, 60_000);                     // heartbeat 20초 × 3회 누락
};

// onopen 과 onmessage(ping 포함) 양쪽에서 호출한다
onmessage(ev) { kick(); if (ev.event !== 'notification') return; ... }

초기 구현에는 넣지 않는다. 클라이언트 쪽 네트워크가 끊기는 경우(와이파이 끔, 절전)는 OS가 브라우저에 네트워크 변경을 알려 onerror가 즉시 발생하고 재연결된다. watchdog이 필요한 것은 그보다 드문 경우이고, 재연결 상태 관리가 붙으면서 Provider가 눈에 띄게 복잡해지는 데 비해 얻는 것이 적다. 운영 중 "알림이 안 오는데 새로고침하면 온다"는 제보가 나오면 그때 도입한다.

Level 2 — Vite + Nest 1대

Level 3 — 교차 인스턴스 전달 (가장 중요)

main.ts:11이 process.env.PORT || 3000이라 포트만 바꿔 두 개를 띄우면 운영의 2-replica 상황을 그대로 재현할 수 있다.

# B 로 수락 요청 (다른 터미널)

첫 번째 curl에 이벤트가 나타나면 Redis Pub/Sub 교차 전달이 검증된 것이다. 반대로 아무것도 안 나오면 5.4의 채널 구독 또는 발행 경로에 문제가 있다. 인메모리 Subject만으로 구현했을 때 실패하는 것도 정확히 이 지점이다.

proxy_buffering 동작까지 확인하려면 nginx 컨테이너만 띄우고 upstream을 호스트로 돌린다.

8. 운영 관측

현재 모니터링 스택은 Alloy → Loki → Grafana, 즉 로그 전용이다 (provisioning/datasources/loki.yml에 등록된 데이터소스도 Loki 하나뿐). Redis의 PUBSUB CHANNELS는 물어봐야 알 수 있는 값이라 Redis 컨테이너 stdout에는 절대 찍히지 않는다. 따라서 앱이 주기적으로 로그에 남기는 방식으로 관측한다. Loki가 로그에서 숫자를 뽑아 시계열로 만들 수 있으므로(unwrap) 인프라 추가 없이 그래프와 알림이 모두 가능하다.

8.1 sse_stats 로깅 전략

무엇을 찍는가

필드출처의미
evt고정 문자열 "sse_stats" — 라인 필터용 앵커. 이 값이 있어야 인덱스 단계에서 값싸게 걸러진다
localChannels앱 메모리 this.channels.size — 이 인스턴스가 들고 있는 채널 수

두 값을 함께 찍는 것이 이 전략의 핵심이다. 하나만으로는 "커넥션이 많은 것"과 "구독이 새는 것"을 구분할 수 없다.

구현

채널 이름 패턴(noti:*)을 아는 것은 도메인 쪽이므로 module/notifications/notifications.service.ts에 둔다. lib의 RedisPubSubService는 숫자를 세어줄 뿐이다(5.4). 

@Injectable()
export class NotificationsService implements OnModuleInit, OnModuleDestroy {
  private statsTimer?: NodeJS.Timeout;

  onModuleInit() {
    // @nestjs/schedule 을 새로 추가하지 않기 위해 setInterval 사용
    this.statsTimer = setInterval(() => void this.logStats(), 30_000);
  }

  private async logStats() {
    try {
      this.logger.info({
        evt: 'sse_stats',
        localChannels: this.pubsub.localChannelCount,           // 이 인스턴스
        redisChannels: await this.pubsub.countChannels('noti:*'), // 전체 합
      });
    } catch (e) {
      // 관측 실패가 서비스에 영향을 주면 안 된다
      this.logger.warn({ evt: 'sse_stats_failed', err: String(e) });
    }
  }

  onModuleDestroy() {
    clearInterval(this.statsTimer);
  }
}

설계 판단

  • 주기 30초 — 인스턴스당 하루 2,880줄. Loki 보존 14일 기준으로 부담이 없고, 커넥션 수는 급변하는 값이 아니라 이 해상도로 충분하다.
  • 인스턴스 식별은 하지 않아도 된다 — Alloy가 __meta_docker_container_name을 container 라벨로 붙여주므로 (be-nodi-backend_blue-1 / -2) replica가 자동 구분된다. 앱에서 process.env.HOSTNAME을 따로 넣을 필요가 없다.
  • evt를 라벨로 승격하지 않는다 — config.alloy의 stage.labels는 의도적으로 level만 올리고 있다. 라벨을 늘리면 카디널리티가 커져 Loki 인덱스가 나빠진다. 쿼리에서 | json | evt="sse_stats"로 거르는 것으로 충분하다.
  • 실패를 삼킨다 — Redis 질의가 실패해도 알림 기능 자체는 정상 동작해야 한다. 5.5의 "알림 실패가 수락/거절을 롤백하지 않는다"와 같은 원칙이다.
  • 모든 인스턴스가 redisChannels를 조회한다 — 값이 중복되지만 같은 값이라 무해하고, 특정 인스턴스만 조회하게 만드는 리더 선출은 얻는 것에 비해 복잡하다. 쿼리에서 max()로 집계한다.

8.2 Grafana 패널

인스턴스별 활성 채널 수

sum by (container) (
  last_over_time(
    {service=~"backend_.+"} |= "sse_stats" | json | unwrap localChannels [1m]
  )
)

Redis 측 실제 채널 수

max(
  last_over_time(
    {service=~"backend_.+"} |= "sse_stats" | json | unwrap redisChannels [1m]
  )
)

|= "sse_stats"를 | json 앞에 두는 것이 중요하다. 라인 필터가 인덱스 단계에서 먼저 걸러 JSON 파싱 비용을 크게 줄인다. 기존 rules.yml의 nginx 5xx 규칙과 같은 패턴이다.

두 쿼리를 한 패널에 겹쳐 그린다. 벌어짐이 곧 진단이다.

관측해석
redisChannels ≈ Σ localChannels 정상
redisChannels만 단조 증가 5.3 finalize() 구독 해제 누락 — 코드 버그
둘 다 접속자 수를 따라 오르내림 정상. 좀비 커넥션이 섞여 있어도 15분 내 회수된다 (3.4)
배포 후 localChannels가 0에서 회복되지 않음 재연결 실패 또는 nginx 설정 문제

    summary: 'Redis pub/sub 채널 {{ $values.A }}개 — finalize() 누수 확인 필요'
    runbook: 'docker compose exec redis redis-cli PUBSUB CHANNELS "noti:*"'

임계값은 운영 초기 실제 동시 접속자 수를 관찰한 뒤 정한다. 처음부터 숫자를 박으면 오탐이거나 무의미하다. for: 30m을 둔 이유는 비정상 단절 커넥션이 최대 15분간 남기 때문이다(3.4). 그보다 짧게 잡으면 정상적인 회수 지연을 누수로 오인한다.

8.4 Prometheus를 지금 도입하지 않는 이유

정석은 Prometheus + redis_exporter다. redis_pubsub_channels가 그냥 나오고, 메모리 · 이빅션 · 느린 명령까지 딸려온다. Alloy가 prometheus.scrape를 지원하므로 수집기는 재사용되고 저장소만 추가하면 된다. 그럼에도 지금은 도입하지 않는다.

이유 1 — 필요한 것이 숫자 두 개뿐이다

알림 기능 하나를 붙이면서 관측 스택을 확장하는 것은 순서가 뒤바뀐 일이다. 지금 보고 싶은 localChannels / redisChannels는 로그로 충분히 관측되고, 컨테이너 2개(prometheus, redis_exporter) · 볼륨 · 보존 정책 · 메모리 300MB 내외가 그 대가로는 과하다.

이유 2 — 레이턴시는 이미 확보되어 있다

Prometheus 도입 근거로 가장 흔히 꼽히는 항목인데, 이 프로젝트는 nginx/conf.d/default.conf의 json_log에 request_time · upstream_time을 이미 남기고 있어 지금도 계산된다. 

quantile_over_time(0.95, {service="nginx"} | json | unwrap request_time [5m])

이유 3 — 남는 격차를 알고 감수한다

정직하게 말하면 로그 기반에는 구조적 한계가 있다. 앱이 살아있어야 찍힌다는 점이다. 앱이나 Redis가 죽으면 데이터 자체가 사라져 "값이 0"과 "관측 불능"이 구분되지 않는다. Prometheus라면 up{job="redis"} == 0으로 죽었다는 사실이 하나의 시계열이 되고, redis_exporter는 앱과 무관하게 Redis를 관측한다.

지금은 이 격차를 기존 nginx 5xx 알림으로 간접 커버한다 (rules.yml의 nodi-nginx-5xx — 백엔드 미도달 요청을 잡는다). 완전하지는 않지만 현 규모에서는 실용적이다.

도입 트리거

아래 중 하나라도 해당되면 그때는 명확히 필요하다.

  • Redis를 캐시 · 리프레시 토큰 저장소로 더 쓰게 되어 메모리 압박이나 키 이빅션이 우려될 때 — 로그로는 관측 불가능하다
  • SSE 동시 커넥션이 수백 단위를 넘어갈 때 — 30초 로깅 해상도로는 스파이크를 놓친다
  • 서비스 생존 여부를 직접 감시해야 할 때

9. 주의사항

영역이슈대응
FE 훅을 여러 컴포넌트에서 호출하면 커넥션이 그만큼 열린다 Provider 1개로 강제. HTTP/1.1은 도메인당 동시 연결 6개 제한이라 일반 API가 대기에 밀린다
FE 브라우저 내장 EventSource는 커스텀 헤더를 붙일 수 없다 Bearer 헤더 인증이므로 @microsoft/fetch-event-source를 쓴다 (6.1)
FE StrictMode에서 useEffect가 2회 실행 → 커넥션 2개 cleanup의 es.close()로 해소. 개발 환경 한정
FE 탭을 여러 개 열면 탭 수만큼 커넥션이 생긴다 정상 동작(모든 탭이 알림을 받음). 문제가 되면 BroadcastChannel로 리더 탭 선출을 검토
FE onmessage를 catch-all로 쓰면 heartbeat·미래 프레임이 섞여 들어온다 addEventListener('notification')로 이벤트명을 명시 (6.6)
BE 전역 TransformInterceptor가 SSE 프레임을 감싸 event: 이름을 지운다 구현 전 APP_INTERCEPTOR + Reflector로 SSE 라우트 예외 처리 (5.3). 이 수정 없이는 기능 전체가 조용히 실패한다
BE heartbeat를 끄면 죽은 커넥션이 최대 2시간 남는다 20초 주기 유지. 프록시 타임아웃 방지 + 재전송 타이머 트리거 이중 역할 (3.4)
BE 비정상 단절 시 커넥션 회수에 약 15분이 걸린다 TCP 재전송 소진에 의존. tcp_retries2는 전역 설정이라 튜닝하지 않고 모니터링만 한다
BE 인스턴스 2대 — 인메모리 전달로는 절반이 유실 Redis Pub/Sub 필수. 7.2 Level 3에서 로컬 검증 가능
BE 커넥션 종료 시 Redis 구독을 해제하지 않으면 누수 RxJS finalize에서 정리. 배포 후 PUBSUB CHANNELS 수 확인
BE 알림 발행 실패가 수락/거절 API를 실패시킴 트랜잭션 밖 호출 + 예외 삼키고 로깅. DB 저장이 진실의 원천
BE 재배포 시 전체 커넥션이 동시에 끊겨 재연결이 몰린다 롤링 배포로 인스턴스를 번갈아 교체. 2대이므로 한 번에 1대씩
INFRA proxy_buffering 기본값이 이벤트를 지연시킨다 해당 location만 off (5.6)

10. 확장: Web Push

브라우저가 닫힌 상태에서도 수락/거절 결과를 알려야 한다면 SSE를 대체하지 않고 병행한다. 탭이 열려 있으면 SSE, 닫혀 있으면 Web Push가 표준 조합이다.

  • BE web-push + VAPID 키. PushSubscription 테이블 (endpoint unique, p256dh, auth, userId) — 사용자 : 구독 = 1 : N
  • BE 발송은 BullMQ + Redis 큐로 비동기 처리
  • BE 응답 410 Gone / 404 시 구독 레코드 삭제. 방치하면 몇 달 뒤 발송의 상당수가 무효가 된다
  • FE public/sw.js에 두면 Vite가 루트 경로로 서빙한다. 권한 요청 UX와 구독 등록/해지 토글 필요
  • 페이로드 상한 약 4KB(안전선 3KB). 큰 데이터는 ID만 보내고 Service Worker에서 fetch
  • iOS Safari는 사용자가 홈 화면에 추가해 PWA로 설치해야만 동작한다. OS 제약이라 우회 불가 — iOS 비중이 크면 설치 유도 동선을 함께 설계해야 한다
